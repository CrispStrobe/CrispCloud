# Read-only ISO multi-extent files

CrispCloud can browse and read ordinary ISO 9660 files represented by multiple
directory records. Each complete chain appears as one member with its combined
size. Buffered previews retain their existing size limit, and positional
extraction streams the file sections in record order. Joliet names and the
existing ordinary Rock Ridge names/permissions are supported.

The implementation follows the file-section ordering and consistency rules in
[ECMA-119, third edition](https://www.ecma-international.org/wp-content/uploads/ECMA-119_3rd_edition_december_2017.pdf),
sections 6.3, 6.5, 9.1.6, 9.2 and 9.3. Directory records for the same file occur
consecutively, apart from zero sector padding. The final record clears the
multi-extent flag. Physical sections need not be adjacent or increasing and may
repeat; their directory order determines the logical contents. Directories
remain single-extent.

## Bounded supported profile

- Each section must fit the declared image and use the same raw identifier and
  non-continuation flags. The displayed recording time, Rock Ridge name and mode
  must agree. This intentionally narrower metadata profile avoids selecting a
  preferred value from contradictory section records.
- The profile covers ordinary regular files. Extended attribute records,
  record-structured/protected chains, special files, interleaving and references
  to another volume are refused. Unsafe names, missing final records and a
  different record interrupting a chain also fail opening.
- A logical file is capped at **8 GiB**, with default metadata ceilings of
  **1,024 sections per file** and **100,000 section records per image**. Section
  records are charged independently of the logical member count. Existing
  directory, name, nesting and SUSP budgets remain in force.
- Listing does not read payload bytes. A read checks the complete logical size
  before fetching a section. A streaming request reads bounded chunks and
  verifies exact logical length through the shared archive interface.

This reader extension leaves ISO creation and editing on their inspected
single-extent profile. The existing writer inspector explicitly refuses
multi-extent records, and a regression checks that boundary. UDF-only images,
multi-volume sets and broader filesystem structures remain outside this change.

## Executed verification

On Flutter 3.47.8 / Dart 3.13.7, **123 focused ISO reader, writer and streamed
workflow tests passed**, including 32 new multi-extent cases. Strict scoped
analysis found no issues. New cases exercise ordinary, Joliet and Rock Ridge
chains, physical reordering/repetition, directory-sector padding, zero-length
sections, total read limits, source cleanup, malformed metadata and writer
refusal.

The existing app dependency lockfile was used. Flutter tests ran through the
documented local archive native profile, which disables the optional ebook hook
and selects verified local SQLite and pinned libsmb2. The wrapper restored both
root manifests byte-for-byte. An initial `dart run` of the independent fixture
emitter reached the unrelated optional ebook hook and failed because Cargo is
unavailable. The pure-Dart tools were then executed directly with the resolved
package configuration; those tools import no native application service.

The portable verifier passed on both the Dart VM and actual compiled JavaScript
under Node. Its synthetic positional source retains the exact logical size
**4,294,969,344 bytes**, rejects buffered reading and streams a 256-byte prefix
using bounded requests. This checks arithmetic and source access; it does not
claim a complete physical extraction of a file above 4 GiB.

Four separately authored ISO fixtures were also extracted by installed **7-Zip
26.06**. They cover plain records, directory-sector padding, Joliet and Rock
Ridge. Every output namespace and all 8,207 member bytes matched the independent
fixture expectation. The common payload SHA-256 is
`080d7261e90e497d215679981b4ad0e9232b43e5e11a3679f68c35eb1c59e91d`.
The fixture generator does not call a CrispCloud reader or writer. These are
specification-based fixtures checked by an independent decoder, rather than
images generated by that external tool.

The checked-in reproduction tools are:

- `test/support/verify_archive_iso_multiextent.dart`: real VM/JavaScript reader
  acceptance, malformed chains and large logical size handling.
- `test/support/emit_archive_iso_multiextent.dart`: emits four images and their
  expected namespace, size and SHA-256 manifest.
- `test/support/check_archive_iso_multiextent.py`: extracts those images with a
  supplied installed 7-Zip and checks complete output contents.

Example commands from the app root after resolving its pinned dependencies:

```sh
dart --packages=.dart_tool/package_config.json test/support/verify_archive_iso_multiextent.dart
dart compile js --packages=.dart_tool/package_config.json -O1 -o /path/to/check.js test/support/verify_archive_iso_multiextent.dart
node -e 'globalThis.self=globalThis; require(process.argv[1]);' /path/to/check.js
dart --packages=.dart_tool/package_config.json test/support/emit_archive_iso_multiextent.dart /path/to/fixtures
python3 test/support/check_archive_iso_multiextent.py --input /path/to/fixtures --sevenzip /path/to/7zz
```
