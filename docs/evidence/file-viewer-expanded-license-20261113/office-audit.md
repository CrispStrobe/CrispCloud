# File Viewer office formats: runtime and license audit

Audit target: `flyfish-dev/file-viewer` commit **d264009ca6efb3daed79a39d1ae63133e0f25558**, File Viewer packages **3.3.3**. Read-only source inspection, 2026-11-13. No integration or dependency changes made by this audit.

## Findings for CrispCloud

Accepting MIT, BSD and similar permissive licenses plus MPL makes **WordPerfect, Hangul, Apple iWork, legacy Excel/XLSB, DBF and FODS** plausible additions. It also allows selected improvements from the MIT legacy DOC engine and MIT RTF engine. These are predominantly browser TypeScript/DOM implementations; their availability does not make them drop-in Flutter widgets.

CrispCloud already has native DOC/DOT, RTF, DOCX/DOCM/DOTX/DOTM, XLSX/XLSM/XLTX, PPT/PPS/POT, PPTX/PPTM/POTX, ODT/ODS/ODP and EPUB routes. Contrary to the earlier broad summary, its current `ViewerMode.office` list and `parseOfficeDocument` switch do **not** implement BIFF `.xls`, `.xlsb`, `.dbf` or `.fods`. Its legacy PPT preview is active-slide **text**, not positioned slide rendering.

Its existing DOC package is more substantial than a basic text extractor: `packages/legacy_doc_parser` is authored under MPL-2.0, with explicitly retained MIT compound-container source and 0BSD formatting adaptations. It already models headers, footers, notes, comments, nested tables, revisions, images, supported OfficeArt and separate DOCX/DOCM conversion. Replacing it wholesale with File Viewer's MIT DOC renderer is not justified by this audit. The practical opportunity is to compare isolated missing behaviors and bring over tested improvements.

## Precisely how legacy DOC renders

1. `word/src/index.ts` invokes `resolveWordContainer`. ZIP signatures dispatch to DOCX; namespace-validated Word 2003 XML goes through the WordML-to-DOCX adapter; HTML/plain-text documents with old suffixes have separate sanitized/text paths. Genuine OLE/CFB routes to `wordDoc.ts`. RTF is a separate opt-in route; a `.doc` name alone does not prove binary Word.
2. `wordDoc.ts` calls `parseMsDocToHtml(buffer,{renderOptions})`. It sets review mode and blocks external links/resources by default. It does not pass the library's optional `workerClient`, so this path parses on the main thread.
3. `doc/src/msdoc/parser.ts` calls `parseCFB`, gets `/WordDocument`, reads FIB flags, and rejects `fEncrypted`. It chooses `/0Table` or `/1Table`, gets `/Data`, parses the CLX piece table and reconstructs text. STSH/font tables and CHPX/PAPX formatting runs supply character/paragraph/table properties.
4. It constructs paragraph/table blocks and assets. Supported PICF/OfficeArt pictures include raster formats and partial EMF/WMF-to-SVG conversion; OLE attachments are represented, not launched. Body content and nonempty textbox/header-textbox stories enter this output; textbox positions are explicitly unavailable and text is linearized after body content. Do not infer full header/footer/note layout from the library's recognition of story lengths.
5. `renderMsDoc` converts the normalized model to HTML/CSS. `mountWordDocument` wraps explicit break markers in page-like sections, sanitizes the resulting markup through DOMPurify and mounts it. The wrapper uses a nominal 794×1123 page surface with browser fonts and adaptive sizing. This is reconstructed HTML, not the Microsoft Word layout engine.

The main implementation is MIT, not Apache, even though the host Word renderer is Apache. Its exact license notice is `Copyright (c) 2026 msdoc-viewer contributors`. See O2–O4.

## Precisely how WordPerfect renders

1. `wordperfect.ts` calls `parseWordPerfectWithWorker`. The default path uses an ES-module Worker, copies/transfers document bytes and terminates the Worker after completion, abort or timeout (default60 seconds). `useWorker:false` or absent Worker support goes straight to approximate text fallback; it does **not** run libwpd on the main thread.
2. The Worker lazy-imports `libwpd.mjs`, fetches the configured local/self-hosted WASM, allocates input/output slots and calls `_xberg_wpd_is_supported` then `_xberg_wpd_extract_document`.
3. The C++ bridge feeds libwpd through librevenge callbacks. It serializes a versioned binary event stream: metadata and text/style/list/table/header/footer/note/link events. This is neither DOCX nor PDF nor LibreOffice HTML.
4. `libwpd.ts` validates/decodes the event stream into `WordPerfectDocument`. The decoder guards counts at1,000,000 events/metadata items and strings at128MiB. `wordperfect.ts` creates text nodes/spans/headings/tables. It allows only http/https/mailto links in decoded runs.
5. Fidelity losses are visible in code: the bridge's page spans, embedded fonts, frames, binary objects, equations and vector graphic callbacks are empty. Renderer output places body paragraphs first and then all tables, so original paragraph/table interleaving is lost; table cells are plain text, with spans but not rich runs. Headers, footers and notes occupy dedicated generic regions. This is useful structured reading, not original WordPerfect typesetting.
6. Encrypted documents produce explicit failure. Structured libwpd failures caught inside the running Worker fall back to signature-checked approximate text with a warning in the model. Worker startup errors, timeouts and aborts reject instead of entering that fallback. The current DOM renderer does **not display those warnings**. A CrispCloud integration should show engine/fallback status, rather than presenting recovered text as complete output.
7. The fallback accepts a WPC signature and has128MiB input/100,000-paragraph limits. The WASM path allocates before this fallback limit, so carry CrispCloud's own bounded read and resource constraints into the bridge. The catalog lists WP4.2/5.x/6+; no independent native corpus was exercised for this audit. `.wpt` is not a route in the pinned catalog.

## Audit limits and practical selection

- Retained physical Worker grant files for Hangul/iWork/XLSX are stronger evidence than wrapper licenses, but are inventories of bundled inputs, not a complete installed dependency inventory. The pinned lock resolves additional JSZip helpers (lie3.3.0, pako1.0.2, readable-stream2.3.6, setimmediate1.0.5); those helpers and further MIT/ISC transitive packages need notice retention if redistributed. Their original packages were not all unpacked independently here.
- Exact `e-virt-table1.4.17` original LICENSE and package manifest were subsequently verified from the npm tarball; both confirm MIT. The tarball matches the pinned File Viewer lockfile integrity. No NOTICE file is present.
- Exact `@file-viewer/docx0.3.39` original LICENSE and package manifest were subsequently verified from the npm tarball; both confirm Apache-2.0, with Copyright2016–2023 Volodymyr Baydalka retained. The tarball matches the pinned File Viewer lockfile integrity. No NOTICE file is present. This closes the engine-package grant gap; its separately shipped dependency files still retain their own grants.
- PPT1.0.2 compiled runtime is already retained with its full Apache LICENSE/NOTICE and no production dependencies. Do not confuse it with the older restricted native engine just because wrapper compatibility option names still include `wasmUrl` and `fontUrl`.
- Upstream's ODF extraction is not an appealing replacement for CrispCloud's native ODF parser. Existing native DOC likewise should remain unless a corpus demonstrates a specific improvement.
- For truly new formats, choose a bounded standalone model and native Flutter renderer where feasible. WPD requires a native/WASM engine boundary; iWork/Hangul are larger JS parser ports. DBF or XLS/XLSB can be staged independently. No office slice examined here requires an external document conversion service.
