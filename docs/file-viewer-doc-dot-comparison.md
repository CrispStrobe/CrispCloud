# File Viewer DOC/DOT versus CrispCloud's legacy DOC parser

Audit and differential probe: 13 November 2026. This compares executable source and a selected fixture corpus, not screenshots or a claim of universal Word fidelity.

## Recommendation

Keep `legacy_doc_parser` as CrispCloud's primary binary Word engine. Its validated document model, auxiliary stories, list reconstruction, revision provenance, bounded input/output, and editable DOCX conversion are substantial capabilities that File Viewer's binary DOC renderer does not replace. There are nevertheless concrete improvements to take from File Viewer: broader container detection, useful textbox recovery, explicit final/original revision views, and selected font/metafile handling. The two parsers also make different compatibility choices: three existing File Viewer fixtures open with its parser but fail our current strict parser. Those are actionable regression cases, not grounds for calling either engine uniformly better.

The most immediate issue is in **CrispCloud's adapter**, rather than its parser. `LegacyWordDocument.plainText` and `safeHtml` deliberately contain the main story only. The parser separately exposes headers, footers, notes, comments, and textboxes through `stories`, but `parseOfficeDocument()` forwards only the main-story values. File Viewer linearizes textbox stories after the body, so some textbox-heavy documents show more text there even when our parser has already recovered that text. Exposing our existing stories with clear labels would close that gap without replacing the parser. [Native model][native-model] · [CrispCloud adapter][app-adapter] · [File Viewer parser][fv-parser]

## How they execute

**File Viewer:** the Word wrapper first identifies the actual container. Binary OLE input goes to `parseMsDocToHtml()`: CFB streams → Word FIB and piece table → text plus paragraph/run/table/image properties → a JavaScript document model → generated HTML/CSS → sanitization → browser layout. It does not invoke LibreOffice, Microsoft Word, a server conversion service, or a DOC-to-DOCX conversion for binary DOC. Although the lower-level engine has a Worker API, the inspected default Word wrapper calls the parser directly. Its page-like presentation uses 794 × 1123 CSS-pixel defaults and explicit break markers; it is not reconstruction of arbitrary original Word pagination. [Word dispatch][fv-word] · [Word DOC mount][fv-word-doc] · [Engine viewer][fv-viewer]

**CrispCloud:** the `.doc`/`.dot` adapter directly calls the pure-Dart `parseLegacyWordDocument()`. A bounded CFB reader and validated binary source feed the structured parser. The result includes main blocks, independently identified auxiliary stories, section and numbering information, fields/bookmarks, review information, media/source evidence, main HTML/text, and per-story HTML/text. The F3 adapter currently passes only main HTML/text and a partial-preview notice. A separate parser capability can produce editable DOCX (and a supported macro-preserving DOCM path); that richer conversion behavior should not be confused with what the current F3 HTML preview paints. [Parser entry][native-entry] · [Structured parser][native-parser] · [Native HTML renderer][native-render] · [CrispCloud adapter][app-adapter]

## Capability comparison

| Area | File Viewer at the pinned commit | Our parser and current CrispCloud behavior | Practical conclusion |
| --- | --- | --- | --- |
| Binary DOC and DOT | Both extensions share binary Word parsing. Template flags are read, but the preview is document content, not template instantiation. | Same parser for DOC/DOT; validates the Word identifier and a set of Word 97-and-later FIB versions. No template instantiation. | A real upstream `template.dot` opened in both engines with equal normalized preview text in this probe. This does not establish every template feature or old Word version. |
| Misnamed and alternative containers | Signature dispatch recognizes ZIP Open XML, OLE binary, Word 2003 WordML, HTML, and plausible plain text. A bounded 64 KiB sample checks the WordML namespace; unrelated XML and RTF are not treated as plain text. WordML is converted to Open XML and rendered through `@file-viewer/docx`. | `.doc`/`.dot` presently go straight to binary parsing. DOCX-family files and RTF have separate extension routes; WordML-in-DOC is not implemented by this path. | A bounded container router would add real compatibility. It should keep explicit format labels and existing safe HTML/RTF boundaries. WordML support is a separate conversion-engine addition, not a binary-parser feature. |
| Main text and encoding | CLX piece decoding handles compressed Word characters and UTF-16 pieces. Font runs distinguish Latin, East Asian and complex-script choices. | Validates piece extents, ordering and coverage; decodes into a combined UTF-16 sequence and validates Unicode. Uses the documented compressed-character mapping rather than treating all bytes as arbitrary locale text. | Both have real binary text extraction. Upstream script/font routing is worth targeted comparison; no global encoding superiority was established. |
| Auxiliary stories | Reads declared story lengths, but emitted content is main plus nonempty textbox/header-textbox stories. Textboxes are appended with `MSDOC_TEXTBOX_STORY_LINEARIZED`; position is unavailable. Ordinary headers, footers, footnotes, endnotes and annotations are not assembled into its rendered body. | Models referenced auxiliary stories and their source identities, including note/comment references and header/footer variants. **Current F3 drops these stories** when forming its `OfficeDocument`. | Expose stories from our existing model before adopting another parser. Label their role and keep ambiguous placement explicit. |
| Styles and fonts | Resolves style inheritance and paragraph/run/table properties into browser CSS; has script-sensitive font selection and browser fallback. | Models character/paragraph styles, inheritance, direct formatting, section context and conditional table-style behavior; emits supported properties into HTML and DOCX. | Model breadth and visible CSS are separate. Compare source-defined fonts and measured rendering case by case. Neither controls every installed font or shaping engine. |
| Lists | Preserves `listId`/`listLevel` properties, but the inspected engine does not consume the full binary list/override tables to generate list numbering. | Reconstructs numbering definitions/instances, continuation, restarts, start overrides and supported multilevel behavior. HTML emits resolved markers. | In two real native fixtures our preview includes `1.`, `2.`, etc.; File Viewer's generated HTML contains only the paragraph text. Keep our list resolver. |
| Tables | Builds nested tables, reconciles cell grids and merges, and renders supported borders, padding and vertical text. Has useful WPS-specific compatibility coverage. | Models nested tables, source origins/widths, row and cell properties, twelve conditional style regions, and supported property histories. Strict validations can reject an entire document. | Both support tables substantially. The WPS border-range rejection below is a specific compatibility target; richer models alone do not prove better visible layout. |
| Fields, hyperlinks and bookmarks | Interprets selected `HYPERLINK`/`INCLUDEPICTURE` instructions, hides field instructions, and displays stored results. External links/resources are blocked by default. | Retains field instructions, stored results, bookmarks and references; reports use of stored results. The preview generates fixed markup and never fetches external names. | Neither recalculates arbitrary Word fields. Preserve inert field data and visible stored results, and make any future link policy explicit. |
| Revisions | Renderer supports `all`, `final`, and `original` projections for supported inserted/deleted text and paragraph marks. The Word wrapper defaults to `all`. | Richer source provenance includes authors/dates and supported run/paragraph/section/numbering/row histories. Current HTML marks supported changes but exposes no equivalent general review-mode option through F3. DOCX preservation has separate semantic tests. | File Viewer's visible review controls are useful. Our richer history model should remain; add tested projection views rather than throwing the model away. |
| Raster images and OfficeArt | Extracts supported picture and OfficeArt data, renders raster/vector images, and may expose inert embedded attachments. | Retains bounded assets, picture occurrences, drawing and object/VBA evidence; renders supported pictures. Many editable drawing capabilities belong to the model/DOCX path, not the HTML preview. | Both have partial graphics previews. The quarter-turn image fixture produced one native `<img>` and none upstream; counting tags does not prove orientation or placement fidelity. |
| EMF/WMF | Converts a substantial set of vector/text/bitmap records to SVG. Unknown record cases can be skipped, leaving a partial preview. | Validates bounded records and retains native image bytes. Supports a narrower documented preview subset; an unknown preview record invalidates the complete SVG preview rather than silently disappearing. | Selective upstream GDI features may improve previews, but port with existing record/output budgets and unsupported-record disclosure. A visible partial SVG is not automatically more faithful. |
| Encryption and obfuscation | Rejects `fEncrypted`; reads `fObfuscated`, but that second flag is not independently rejected at the inspected parse entry. No password/decryption API in this binary DOC route. | Rejects both encrypted and obfuscated flags (`0x8100`) and asks for an unlocked copy. | Do not advertise encrypted DOC support. Keep the stricter rejection if integrating upstream code. |

## New differential probe: concrete results

The probe ran the same unchanged bytes through both parsers, generated HTML, and counted structural output. It used **19 deliberately selected existing fixtures** from both repositories: lists, tables, stories, pictures, revisions, a template, and known producer/regression cases. Every input's SHA-256 is retained, and the harness checks that source bytes did not change. Each subprocess has a 20-second timeout. It records compact metrics rather than publishing the documents' text or generated HTML.

**File Viewer returned a model/HTML for 19/19; our parser did so for 16/19.** Eight of the sixteen mutually accepted cases have equal whitespace-normalized generated preview text. These numbers describe this diagnostic selection only. They are not a representative compatibility percentage, a benchmark, or an image/layout comparison. “Accepted” also does not mean every picture, field, story or list label was retained.

| Fixture / observation | Our parser and current main preview | File Viewer | What the evidence establishes |
| --- | --- | --- | --- |
| `list-continue.doc` | Text includes `1. P1 2. P2 3. P3 4. P4 5. P5`. | Text includes `P1 P2 P3 P4 P5`. | Our generated markers survive; upstream loses the generated list labels in this fixture. |
| `list-restart.doc` | Markers are `1, 2, 7, 8, 3, 9`; also emits `numberingNotReconstructed` for the fixture's unsupported aspect. | Paragraph text without generated markers. | Useful native numbering output, with a retained limitation rather than a blanket success claim. |
| `linked-textboxes-extended.doc` | Main preview has 70 normalized characters; a separate 191-character textbox story exists in the model. | 262 normalized preview characters, including linearized textbox text; warns about placement. | The current CrispCloud adapter hides real recovered content. Counts use different normalization for per-story and rendered text and are not expected to add exactly. |
| `word14-margin-origin.doc` | Main preview has no visible text; six textbox stories remain in the model. | 111 normalized preview characters from linearized boxes. | Another clear adapter gap; it is not evidence that our parser failed to extract those boxes. |
| Header/footer/note fixtures | Auxiliary content is preserved separately; current main HTML excludes it. | Main HTML excludes ordinary header/footer/note stories too. | Our model contains more usable content than either inspected default preview displays. |
| `floating-quarter.doc` | One generated image element. | No image element. | Native image preview presence is better for this one fixture; placement/rotation was not visually checked. |
| `image-embedded.doc` | Two image elements and 43 normalized text characters. | Same image count and normalized text. | Agreement on these measurements, not complete image equivalence. |
| `template.dot` | Parses 235 paragraphs, one table and 15 cells; normalized text length 11,135. | Same counts and normalized text. | Actual DOT-positive evidence for both engines. |
| `image-linked.doc` | Rejects: `Unsupported Word picture mapping mode.` | Parses readable text, with no image in the HTML. | An unsupported linked-picture mode currently blocks all native text. A bounded placeholder/recovery path could help; no external image fetch is needed. |
| `github-34-wps-table.doc` | Rejects: `Invalid Word cell border range.` | Parses 81 paragraphs and one table. | A producer-specific border-range compatibility case worth investigating with raw-byte evidence. |
| `github-171-textbox-resume.doc` | Rejects: `Unresolved Word textbox shape reference.` | Parses 28 textbox paragraphs, 454 normalized characters, with a linearization warning. | A content-recovery path could retain text while explicitly withholding unresolved shape placement. |

The upstream tracked-revision fixture provides a useful additional check: upstream `final` and `original` HTML projections have normalized text exactly matching its independently saved accepted/rejected DOC fixtures, at 275 and 308 characters respectively. Both saved reference files also have equal normalized preview text between the two engines. This validates those specific text projections; it does not validate all formatting histories, moves, comments or tracked table structure. [Upstream revision fixture provenance][fv-revision-fixtures]

The [probe evidence](evidence/file-viewer-doc-dot-comparison-20261113/README.md) contains the complete safe result manifest, fixture hashes, harnesses and reproduction commands. Raw generated document content remains outside the repository. The three native failures should become carefully licensed regression fixtures or references before parser fixes are implemented.

## Existing native evidence, and what it does not prove

Our parser already retains a substantially broader fidelity program than this quick comparison: authored binary controls, source provenance, independent schema checks, native-render comparisons, original-versus-bridge attribution, and repeated DOC/DOCX import cycles. Its integrated receipt records **809 Dart tests, 162 Python tests, 51 JavaScript media checks and 218 required SDK outputs**. A retained 24-input native checkpoint completed all initial and 72 repeat imports, matched all initial page counts, and had six initially exact RGB/text/geometry comparisons. Strict structural differences remain recorded. These are **existing versioned receipts, not tests rerun for this comparison**. [Native fidelity status and receipts][native-fidelity]

That distinction matters. Rich section, textbox, shape or revision data in the model can improve editable DOCX conversion without appearing in F3. Matching a native page count does not imply identical placement. An exact result on six fixtures does not imply universal rendering fidelity. Conversely, File Viewer's ability to recover readable text from our three rejection cases is useful even when its page layout or numbering is incomplete.

## Proposed changes, in order

1. **Expose existing auxiliary stories in CrispCloud.** Add clearly identified notes, comments, headers/footers and textboxes to the legacy Word preview, preserving source order/identity and distinguishing content display from positioned layout. Add the two successful textbox fixtures as integration checks so that body-only output cannot regress unnoticed.
2. **Investigate the three native rejection cases independently.** Preserve malformed-input and allocation guards. For an unsupported picture mapping mode, retain text and show an unavailable-image notice if the surrounding record is valid. For an unresolved textbox shape, consider a labeled unpositioned story only when its text range is independently valid. Treat the WPS border case as a narrow producer-compatibility rule backed by positive and negative controls.
3. **Add bounded Word-container detection outside the binary engine.** Detect actual binary/ZIP/WordML/HTML/text signatures before choosing the existing reader. WordML needs a separately reviewed conversion/render path. Never route unrelated XML or RTF into a convincing but incorrect text document just because the suffix is `.doc`.
4. **Offer review projections using our preserved model.** Build `all`, `final`, and `original` views with independent accepted/rejected text and paragraph-boundary controls. Keep author/time/history data, and state limitations for unsupported topology or formatting histories.
5. **Port selected font/metafile improvements only against measured gaps.** Script-aware font fallback and additional GDI records are candidates. Preserve unsupported-record reporting, inert resources, output budgets and exact source/license attribution. Test visible rendering independently of model counts.
6. **Keep native conversion and preview validation distinct.** Maintain DOCX/schema/native round-trip gates for conversion and add F3/browser rendering checks for visible preview behavior. A fallback engine, if later added, should identify that a recovered preview is approximate and report unavailable content.

No parser/runtime code was changed as part of this comparison.
